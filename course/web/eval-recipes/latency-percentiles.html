Latency p50/p95/p99

Cost & latency

cost-latency starter
When to use: Every interactive agent. Means lie; only percentiles tell the user-perceived story.
What it measures: End-to-end response time distribution from user input to final response.

Setup

  1. Stamp every request with start/end timestamps including all tool calls and LLM hops.
  2. Aggregate per route/intent — global percentiles hide critical-path issues.
  3. Compute p50, p95, p99 over rolling 5-minute windows.
  4. Separately track time-to-first-token (TTFT) for streaming UX — it's what users feel.
  5. Compare against budget; alert when p95 exceeds it for 3 consecutive windows.

Code template

typescriptexport function percentiles(latencies: number[], ps = [50, 95, 99]) {
  const sorted = [...latencies].sort((a, b) => a - b);
  return Object.fromEntries(ps.map((p) => {
    const idx = Math.min(sorted.length - 1, Math.floor((p / 100) * sorted.length));
    return [`p${p}`, sorted[idx]];
  }));
}
// Usage:
const stats = percentiles(window.map((r) => r.endMs - r.startMs));
// { p50: 1200, p95: 4500, p99: 12000 }

Acceptance threshold

p95 ≤ target SLA; p99 ≤ 3× p95; TTFT ≤ 1s for streaming UX.

Pitfalls

⚠️ Tracking averages instead of percentiles
Fix: Averages are useless for latency; only percentiles match user experience.
⚠️ Combining routes inflates p99
Fix: Per-route percentiles; one slow tool drags the global.
