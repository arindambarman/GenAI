Tool failure recovery eval

Behavior & tool use

behavior intermediate
When to use: Any agent that depends on flaky external tools (APIs, databases, web fetches).
What it measures: Whether the agent gracefully handles tool failures (retries, alternative tools, user-visible degradation) instead of crashing or hallucinating.

Setup

  1. Build a fault-injection harness that returns errors on a controlled subset of tool calls (timeouts, 500s, malformed responses).
  2. For each fault type, score the agent's recovery: (a) detected, (b) appropriate action (retry/fallback/give up gracefully), (c) user-visible explanation.
  3. Cover at least: transient error, hard error, malformed JSON, timeout, rate-limit.
  4. Track recovery rate per fault type.

Code template

typescripttype Fault = "timeout" | "500" | "malformed" | "ratelimit";

export function withFault(realTool: Tool, fault: Fault): Tool {
  return async (args) => {
    if (fault === "timeout") return new Promise((_, rej) =>
      setTimeout(() => rej(new Error("ETIMEDOUT")), 10000));
    if (fault === "500") throw Object.assign(new Error("Internal Error"), { status: 500 });
    if (fault === "malformed") return { __raw: "<<not-json>>" };
    if (fault === "ratelimit") throw Object.assign(new Error("Rate limited"), { status: 429 });
    return realTool(args);
  };
}

Flow

graph LR
  CASE[Eval case] --> FAULT[Fault injector<br/>timeout/500/malformed/429]
  FAULT --> AGENT[Agent under test]
  AGENT --> CLASSIFY[Recovery class:<br/>retried · fell back · gave up · crashed]
  CLASSIFY --> SCORE[Per-fault recovery rate]

Acceptance threshold

Graceful-recovery rate ≥ 95% per fault type; zero hallucinated answers when tools fail.

Pitfalls

⚠️ Agent hallucinates an answer when retrieval fails
Fix: Detect by checking that responses include no fact-claims when tools all failed.
⚠️ Retry storms exceed rate-limit budget
Fix: Test retry policy under rate-limit faults too.
